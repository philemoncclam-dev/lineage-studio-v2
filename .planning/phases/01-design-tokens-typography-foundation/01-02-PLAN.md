    needed to cover all four surface tiers plus both border tokens, and three more for the
    text tiers. This is an extension of the sketch, not a departure from it — every value
    still comes from a spec table row.

    multi-layer shadows from the UI-SPEC's Elevation Model section verbatim. The dark

  <behavior>
    The audit is dependency-free Node (Node 24 is the local runtime) and exits non-zero on
    any failure. Expected behaviour:

    - Given the shipped tokens.css, `node scripts/audit-tokens.mjs` exits 0 and prints a
      report.
    - Given a tokens.css where two tokens in different channels carry the same value, it
      exits non-zero naming both tokens.
    - Given two tokens in different channels whose OKLCH values are near-identical but not
      byte-identical, it exits non-zero — except for the one allowlisted silver/accent pair.
    - Given a channel with zero or one member, it exits non-zero rather than reporting a
      vacuous pass.
    - Given a token whose value is empty or unparseable, it exits non-zero.
    - Given a pair whose computed ratio is exactly at the threshold, it PASSES.
    - Run twice on unchanged input, stdout is byte-identical.
    - `--self-test` runs every detector against inlined known-bad and known-good fixtures
      and exits non-zero if any detector fails to fire on its known-bad fixture.
  </behavior>
  <action>
    Create `frontend/scripts/audit-tokens.mjs`, a dependency-free ES module run by Node,
    and add `"audit:tokens": "node scripts/audit-tokens.mjs"` to `frontend/package.json`
    scripts. It parses `src/styles/tokens.css` and runs five checks. Exit code is 0 only if
    all pass; every failure is printed with the offending token names.

    **Colour maths.** Implement OKLCH → OKLab → linear sRGB → sRGB using the reference
    OKLab matrices, and the WCAG 2.x relative-luminance and contrast-ratio formulae. After
    converting to linear sRGB, clamp each channel into the 0..1 gamut BEFORE computing
    luminance — the light accent sits on the sRGB boundary and the browser clamps it
    identically, so an unclamped ratio would describe a colour that never paints. Resolve
    each `light-dark(a, b)` primitive into two evaluated colours (light = first argument,
    dark = second) and resolve each tier-2 `var()` reference back to its primitive, so all
    checks operate on evaluated values rather than on source text.

    **Check 1 — single definition site.** Every token name appears exactly once as a
    declaration. This is the invariant that goes red if a future phase reintroduces a
    duplicated definition block; it is the recorded companion test for plan 01-01's
    assumption-delta promote decision.

    **Check 2 — cross-channel collision.** Assign every colour token to exactly one
    channel: `domain`, `edge`, `state` (accent tokens), `surface`, `text`, `status`. A
    token that matches no channel is a hard failure, not a skip. Compare every cross-channel
    pair, per theme, on two axes: exact value equality, and near-equality (compute the
    OKLCH distance and fail when hue is within a small threshold AND chroma and lightness
    are also within small thresholds — near-equal must collide, not merely exactly-equal).
    Allowlist exactly one pair by name with its reason recorded in the source: the silver
    domain against the accent, whose hues are close but whose chroma differs by roughly
    4-5x. Fail if any channel has fewer than two members, or if the allowlist references a
    token that no longer exists — both are vacuous-pass conditions.

    **Check 3 — WCAG AA contrast.** For each theme, compute the ratio for: each of the
    three text tiers against canvas, surface-1, surface-2 and surface-3; border-strong
    against surface-1; the accent against canvas; and each domain and edge token against
    canvas. Thresholds are inclusive: normal text passes at greater-than-or-equal 4.5,
    meaningful non-text at greater-than-or-equal 3. Exempt exactly one token by name with
    its reason inline: the derives edge token. Additionally compute at least the two
    composited cases the UI-SPEC works through — a chip background produced by mixing a
    base token into surface-1 at 14 percent in OKLCH, with primary text over it — and
    assert those composited ratios rather than the base token's. A pair where one operand
    is transparent must be composited against its stated backdrop; it must never be
    skipped and `transparent` must never be treated as a colour.

    **Check 4 — colour-blind separation.** Apply full-severity protanopia and deuteranopia
    simulation matrices in linear RGB to all four domain tokens and all three edge tokens,
    in both themes. For every pair whose simulated hue falls into the same cluster, assert
    the simulated lightness gap clears the perceptibility floor the UI-SPEC uses. Print
    every measured gap so the numbers are auditable, not just a pass/fail.

    **Check 5 — value well-formedness.** Every parsed token value is non-empty and parses
    to a colour or a known non-colour form. An empty or unparseable value is a failure.

    **Determinism.** Sort every collection before printing — token names alphabetically,
    pairs by their sorted name tuple, themes light-then-dark. Two runs on unchanged input
    must produce byte-identical stdout.

    **Self-test.** Support a `--self-test` flag that runs each of the five checks against
    small inlined fixture strings: one known-bad and one known-good per check. It exits
    non-zero if any check fails to flag its known-bad fixture or wrongly flags its
    known-good one. This proves the detectors have teeth before they are trusted.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| token source file → audit script | The audit reads and parses a file that later phases will edit; a parse gap becomes a silent pass |
| audit script → CI / seal decision | A green audit is taken as proof of accessibility and collision-freedom |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-06 | Spoofing | `audit-tokens.mjs` vacuous pass | high | mitigate | A parser that silently matches nothing would report green on an empty or renamed token file. Mitigated by check 2 failing when a channel has fewer than two members, check 5 failing on empty/unparseable values, a channel-assignment miss being a hard failure rather than a skip, and the `--self-test` mode machine-proving each detector fires on a known-bad fixture before the audit is trusted. |
| T-01-07 | Repudiation | Non-deterministic audit output | medium | mitigate | Unstable ordering makes a diff meaningless and lets a regression hide in noise. Every collection is sorted before printing and the acceptance criteria require two consecutive runs to be byte-identical. |
| T-01-08 | Tampering | Allowlisted contrast/collision exemptions | medium | mitigate | Exactly two exemptions exist (the silver/accent near-hue pair, the derives edge token), both named explicitly in source with a written rationale, and the audit fails if an allowlist entry names a token that no longer exists — so an exemption cannot outlive its subject. |
| T-01-09 | Information disclosure | Colour tokens leaking data | low | accept | Tokens are static presentational constants with no data dependency and no user input path. |
| T-01-10 | Tampering | Audit script executed by the build | low | accept | `audit:tokens` is a local, dependency-free Node script under version control in the repo; it introduces no new third-party code and no network access. |
</threat_model>

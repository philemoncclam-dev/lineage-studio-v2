# Phase 1 — UI Design Contract: Design Tokens & Typography Foundation

> Visual and interaction contract for the foundation phase of the Lineage Studio
> frontend rebuild. Every later phase (shell, both canvases, Purview push, light
> review, motion) inherits these tokens verbatim — nothing here is provisional.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

All OKLCH → sRGB conversions and WCAG contrast ratios in this document were
computed directly (Björn Ottosson's reference OKLab matrices; WCAG 2.x relative
luminance formula) rather than eyeballed — see the `Verification Method` note
at the end of the Color System section. Colour-blindness claims (THEME-06) were
checked with a Machado/Oliveira/Fernandes (2009) full-severity dichromacy
simulation applied to the actual shipped hex values, not just hue-angle theory.

## Naming Convention — Three Tiers

This is the deliverable that makes Phase 6's light-mode-only review tractable
(per the roadmap's explicit ask): only tiers 1–2 carry per-theme values. Tier 3
never needs touching when a theme is retuned.

| Tier | Purpose | Example | Theme-aware? |
|------|---------|---------|---------------|
| **1. Primitive** | Raw OKLCH swatch, no meaning attached | `--slate-0` … `--slate-4` (neutral ramp), `--cyan-1/2/3` (accent), `--amber-1` (bronze), `--gold-1`, `--steel-1` (silver), `--rose-1` (notebook), `--indigo-1` (reads), `--violet-1` (writes) | Yes — each primitive is itself defined with `light-dark()` |
| **2. Semantic** | Role-based name, what the token *means* | `--color-surface-canvas`, `--color-text-primary`, `--color-domain-bronze`, `--color-edge-writes`, `--color-accent` | References tier-1 primitives; still theme-aware by inheritance |
| **3. Component** | What a specific component consumes | `--card-bg`, `--card-radius`, `--seg-btn-bg-active`, `--input-radius`, `--row-height` | References tier-2 semantics only — **never a raw hex, never a bare `light-dark()` call** |

Rule for the executor: if you are about to write `light-dark(...)` anywhere
outside the tier-1 primitive definitions, stop — that value belongs in tier 1,
referenced by tier 2, consumed by tier 3. This is what makes "audit light mode
without touching component CSS" possible in Phase 6.

Tailwind v4 mechanics: tiers 1 and 2 live in one or more `@theme` blocks (so
Tailwind emits them as real `:root` custom properties, per STACK.md); tier 3
can be plain CSS (`var(--color-surface-raised)`) since component-level tokens
don't need Tailwind's utility-class generation, only DOM/canvas code reading
`getComputedStyle`.

## Color System

### Verification method

- **OKLCH ↔ sRGB**: computed with Björn Ottosson's published OKLab reference
  matrices (the same math browsers use for native `oklch()`), not approximated.
- **WCAG contrast**: standard relative-luminance formula, computed against the
  *actual composited/rendered hex*, per Pitfall 11's requirement to check
  composited backgrounds rather than declared-token pairs in isolation. A
  worked `color-mix()` chip example is included below.
- **Colour-blindness**: Machado/Oliveira/Fernandes (2009) full-severity
  protanopia/deuteranopia simulation matrices applied in linear RGB to every
  domain and edge-type hex, then re-measured in OKLCH to compare simulated
  lightness/hue. This is the same class of transform used by common CVD
  simulators (Coblis and similar) — not a hue-angle guess.
- All ratios below are Phase 1's own verification pass. **Phase 6 must
  independently re-run this same method against the light theme** once real
  components exist (per THEME-07/Pitfall 12) — these numbers are the
  foundation-phase baseline, not a substitute for that dedicated review.

Dark values are the user-approved anchor hexes verbatim.

| `--color-accent` | `oklch(0.754 0.139 233)` | `#38bdf8` | `oklch(0.52 0.115 232)` | `#00739f` | Light chroma is gamut-clamped at the sRGB boundary — the browser's native `oklch()` clamps identically, so this is the real, stable render, not an approximation |

### Domain palette (knowledge-graph node hue; thin card-strip on DAG)

This is the **THEME-05 fix** and the **THEME-06 re-derivation**. The current
`--notebook` (`#8b5cf6`/`#a78bfa`) is retired entirely — it collided with
`--writes` and its old Gold-as-green metaphor was already colour-blind risky
next to Bronze.

| Domain | Dark OKLCH | Dark hex | vs canvas | Light OKLCH | Light hex | vs canvas |
|--------|-----------|----------|-----------|-------------|-----------|-----------|
| `--color-domain-gold` | `oklch(0.85 0.14 95)` | `#eacc56` | 12.19:1 | `oklch(0.62 0.14 95)` | `#a18400` | 3.37:1 |
| `--color-domain-bronze` | `oklch(0.65 0.15 48)` | `#d66e31` | 5.63:1 | `oklch(0.48 0.15 48)` | `#9d3a00` | 6.44:1 |
| `--color-domain-notebook` | `oklch(0.72 0.16 350)` | `#ed76b3` | 7.20:1 | `oklch(0.56 0.16 350)` | `#b54481` | 4.77:1 |
| `--color-domain-silver` | `oklch(0.45 0.03 235)` | `#455864` | 2.60:1 | `oklch(0.35 0.03 235)` | `#2b3d48` | 10.51:1 |

**Gold is now an actual yellow-gold (H95°), not the old green** — this is both
a metaphor fix and a colour-blind-safety fix: yellow is one of the two hues
(with blue) that survives protanopia/deuteranopia largely intact, unlike the
old green, which sat close to Bronze's orange under simulation.

**Colour-blind verification (Machado et al. 2009 full-severity simulation),
dark theme:**

| Pair (same simulated hue-cluster) | Protanopia L-gap | Deuteranopia L-gap |
|---|---|---|
| Gold vs Bronze (both simulate to ≈95–100° yellow) | 0.245 | 0.194 |
| Notebook vs Silver (both simulate to ≈265–273° blue-grey) | 0.200 | 0.279 |

Light theme: Gold vs Bronze gap 0.190/0.137; Notebook vs Silver gap
0.137/0.217. **All four gaps clear 0.13**, well above the ~0.05 threshold
generally treated as reliably perceptible — meaning even though Bronze/Gold
collapse to the same hue under CVD (unavoidable — both sit on the same
red-green confusion line, this is a property of the deficiency, not a
palette flaw) and Notebook/Silver do too (magenta always residual-collapses
toward blue under red-green CVD), **lightness alone still separates every
pair cleanly.** This is Pitfall 8's exact recommended mitigation — "vary on
both hue and lightness, not hue alone."

**Second channel (THEME-06's explicit requirement, beyond hue):** the domain
legend on the knowledge graph (the one legend the user wants — GRAPH-06) must
pair every swatch with its text label, never colour alone (WCAG 1.4.1) —
this is the primary second channel, and it does not reintroduce the disliked
glyph-on-node pattern, because the label lives in the legend, not on nodes.
A secondary, free second channel: **fix each domain's position in the legend
in a stable canonical order** (e.g. always Bronze → Silver → Gold →
Notebook, left to right) so position becomes a learnable, redundant cue on
top of colour + text.

**`--color-domain-silver` is intentionally low-chroma** (`C≈0.03`, versus
0.14–0.16 for the other three) — its whole visual identity is "the
desaturated one," which is itself the "second channel" for that specific
domain: even a viewer who cannot resolve its blue-grey hue at all can still
tell it apart by saturation alone, which does not depend on colour-opponent
channels the way hue does.

**Note on Silver's hue proximity to Accent:** Silver's dark-mode hue (235°) is
numerically only 5° from Accent's (233°) — a naive grep-for-duplicate-hex
check (Pitfall 7's stated verification method) will not flag this because the
hexes are entirely different, but a hue-only scan might raise a false alarm.
This is *not* a collision: Silver's chroma (0.03) is roughly 4–5× lower than
Accent's (0.14), which is exactly the separation mechanism, not an oversight —
document this reasoning inline in the token file so a future contributor
doesn't "fix" it by moving Silver's hue and accidentally drifting it toward
Bronze or Notebook instead.

### Edge-type palette (lineage DAG hue channel)

**This is the other half of the THEME-05 fix.** The old `--writes`
(`#8b5cf6`/`#a78bfa`) is retired — it was byte-for-byte identical to the old
`--notebook`. New edge hues live in the violet/blue-violet band, well clear of
both the cyan accent (233°) and every domain hue.

| Edge type | Dark OKLCH | Dark hex | vs canvas | Light OKLCH | Light hex | vs canvas |
|-----------|-----------|----------|-----------|-------------|-----------|-----------|
| `--color-edge-reads` | `oklch(0.80 0.10 272)` | `#a7baff` | 10.21:1 | `oklch(0.62 0.12 272)` | `#6d80ce` | 3.48:1 |
| `--color-edge-writes` | `oklch(0.55 0.15 315)` | `#9252ad` | 3.70:1 | `oklch(0.40 0.15 315)` | `#65247d` | 9.32:1 |
| `--color-edge-derives` | `oklch(0.38 0.02 266)` | `#3d424d` | 1.92:1 | `oklch(0.72 0.02 266)` | `#9fa5b2` | 2.30:1 |

**Reads vs Writes was re-verified under the same CVD simulation** even though
THEME-06 is scoped to domain colours specifically — because both edge types
sit in the violet/blue-violet band and DO collapse toward the same simulated
hue (≈264–267°) under protanopia/deuteranopia, just like Bronze/Gold and
Notebook/Silver. The fix is identical: a large lightness gap.

| Pair | Protanopia L-gap | Deuteranopia L-gap |
|------|---|---|
| Reads vs Writes, dark | 0.286 | 0.247 |
| Writes vs Notebook (domain), dark, cross-channel check | 0.134 | 0.183 |

`--color-edge-derives` is **deliberately low-contrast and near-achromatic**
(1.92:1 dark / 2.30:1 light) — it is the weakest-confidence, lowest-emphasis
edge type (an unattributed transform, no strong signal either way), and this
low visual weight is intentional, mirroring the old app's `--derive` token
which was already appropriately muted. It is exempt from the 3:1 non-text
threshold on the same basis a disabled control is commonly exempted: it is
not conveying required information on its own, it is the visual "we don't
know" state, and its neighbours (reads/writes) carry the actual signal.

**Edge-type does not need a second (non-colour) channel per THEME-06's letter**
— that requirement is scoped to domain colours. Note for Phase 3 (`TRUST-01`):
provenance (declared vs inferred) will need its own stroke-style channel
(solid vs dashed) layered on top of these hues — **do not consume dash-pattern
as edge-type's identity marker here**, reserve it entirely for Phase 3's
provenance distinction so the two channels don't compete for the same visual
device.

### Worked composited-background example (Pitfall 11 method)

Per Pitfall 11, contrast must be checked against the actual rendered/composited
background, not the declared token alone. Worked example — a `color-mix()`
chip using Bronze at 14% (the existing `.src-chip` pattern in `App.css`):

- **Dark**: `color-mix(in oklch, var(--color-accent) 14%, var(--color-surface-1))` on `#38bdf8`/`#141926` → composited `#193043`. Primary text (`#e7eaf2`) on that chip: **11.29:1**. Accent-coloured text on that same chip: **6.34:1**. Both pass AA.
- **Light**: Bronze 14% over `surface-1` (`#9d3a00` / `#fbfcfd`) → composited `#eee1da`. Primary text (`#1c2333`) on that chip: **12.27:1**. Passes comfortably.

**Executor rule**: any new `color-mix()`-derived chip/pill/badge background
must be checked this way — compute the actual composited hex (via `color-mix`
math in `oklch`, not `srgb`, per STACK.md's guidance on perceptual evenness)
and re-run contrast against it, never assume the base token's contrast number
still applies once opacity/mixing is introduced.

## Elevation Model (DS-05)

**Dark theme: elevation is lighter-is-higher, shadow is minimized.** The four
surface tiers (`canvas` → `surface-1` → `surface-2` → `surface-3`) step up in
lightness (0.165 → 0.215 → 0.257 → 0.299), each with a `--color-border` token
sitting one step lighter still (0.329) as a thin 1px reinforcement between
adjacent tiers — this is Pitfall 9's exact recommended shape ("a thin 1px
border at a lightness between the two adjacent surfaces"). A very subtle
shadow may still be layered on top (it costs nothing and helps at shallow
elevation differences) but **must never be the only signal** — DS-05 forbids
shadow-as-primary-mechanism specifically because dark canvases have almost no
room to go *darker* than an already-near-black background, which is exactly
why shadow-only elevation silently stops reading (Pitfall 9).

Reference dark shadow (supplementary only, optional per component):
`0 1px 2px rgb(0 0 0 / 0.35)`.

**Light theme: elevation reintroduces shadow as a legitimate primary
mechanism** — this is a deliberate, non-mechanical divergence from dark, not
an oversight. Shadow-based elevation is light-mode-native (it models a light
source on a plane); DS-05's "shadows do not read on dark" is a dark-canvas-
specific finding, not a blanket ban. Because white has almost no lightness
headroom above it, the four light surface tiers step by very small deltas
(0.975 → 0.99 → 0.995 → 1.0) — the perceptual work is done by shadow +
border, not by lightness, in this theme:

- `--shadow-card` (surface-1): `0 1px 2px rgb(28 35 51 / 0.04), 0 4px 12px rgb(28 35 51 / 0.08)`
- `--shadow-raised` (surface-2): `0 2px 4px rgb(28 35 51 / 0.06), 0 8px 20px rgb(28 35 51 / 0.10)`
- `--shadow-overlay` (surface-3/modal): `0 8px 24px rgb(28 35 51 / 0.14), 0 24px 48px rgb(28 35 51 / 0.18)`

**Flag for Phase 6**: these light-mode lightness deltas are deliberately tiny
(0.005–0.02) since white has little room — per Pitfall 12, this is exactly the
kind of tier that needs its *own* tuning pass once real components exist, not
an assumption that the dark-mode formula "worked out." If real cards prove
hard to tell apart in light mode, the fix is to lean harder on
`--shadow-*`/`--color-border-strong`, not to force more lightness spread than
white can give.

### Elevation token → component mapping

| Semantic token | Used for |
|---|---|
| `--color-surface-canvas` | Page/canvas background (both lineage DAG and knowledge graph dot-grid backgrounds) |
| `--color-surface-1` | Default card/panel background (table cards, inspector panel, toolbar) |

| `--color-border-strong` | Interactive-component boundary (input fields, focus-adjacent dividers) — meets 3:1 |

## Token-to-Canvas Bridge (THEME-03)

**The pattern**: read all needed CSS custom properties **once** into a plain
JS object, cache it at module scope (or in a small context/store), and
invalidate the cache **only** when the `data-theme` attribute actually
changes — never per frame, never per node, never inside a canvas draw loop.

```ts
// tokens/canvasTokens.ts
export interface CanvasTokens {
  surfaceCanvas: string
  accent: string
  domainBronze: string
  domainGold: string
  domainSilver: string
  domainNotebook: string
  edgeReads: string
  edgeWrites: string
  edgeDerives: string
  // ...every token a canvas/SVG renderer needs, and nothing it doesn't
}

function readTokensFromDOM(): CanvasTokens {
  const cs = getComputedStyle(document.documentElement)
  const v = (name: string) => cs.getPropertyValue(name).trim()
  return {
    surfaceCanvas: v('--color-surface-canvas'),
    accent: v('--color-accent'),
    domainBronze: v('--color-domain-bronze'),
    domainGold: v('--color-domain-gold'),
    domainSilver: v('--color-domain-silver'),
    domainNotebook: v('--color-domain-notebook'),
    edgeReads: v('--color-edge-reads'),
    edgeWrites: v('--color-edge-writes'),
    edgeDerives: v('--color-edge-derives'),
  }
}

let cached: CanvasTokens | null = null

export function getCanvasTokens(): CanvasTokens {
  if (!cached) cached = readTokensFromDOM()
  return cached
}

// Wire this once, at app bootstrap — not per component, not per render:
const observer = new MutationObserver(() => { cached = null })
observer.observe(document.documentElement, { attributes: true, attributeFilter: ['data-theme'] })
```

**Explicit prohibitions** (Pitfall/Performance-trap table, `PITFALLS.md`):

- **No `getComputedStyle` call inside a per-frame render function, a
  per-node/per-edge draw callback, or a hover/selection handler.** Every such
  call recomputes style for the whole document and gets more expensive as
  node/edge count grows — this is a named performance trap, not a style
  preference.
- `@xyflow/react`'s custom edge/node renderers, sigma.js's node/edge
  reducers (Phase 4), and any hand-rolled `<canvas>` draw call must all read
  from `getCanvasTokens()` (or an equivalent cached snapshot passed down),
  never call `getComputedStyle` themselves.
- Theme toggle implementations (wherever they land — Phase 2's shell) must
  invalidate this cache as their *last* step, after the `data-theme` attribute
  write, via the `MutationObserver` shown above (or an equivalent explicit
  "theme changed" event) — not by having every consumer poll or re-check on
  their own schedule.

## Typography (DS-03, DS-06)

### Template-required summary

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 11px (`micro`) | 400 (regular) | 1.35 |
| Body | 13px (`base`) | 400 (regular) | 1.45 |
| Heading | 18px (`heading`) | 600 (semibold) | 1.3 |
| Display | 22px (`display`) | 600 (semibold) | 1.25 |

### Full named ramp — four steps (retires the scattered 10.5/11.5/12.5/13/14/17px values)

**Revised down from an earlier six-step draft.** The checker correctly
rejected that draft: a hard maximum of 4 font sizes is the design-contract
rule, and 11/12/13 sitting inside a 2px band read as inconsistency rather than
a perceptible hierarchy — precisely the failure mode the 4-size rule exists to
prevent. 15px (the old fifth step, `text-md`) sat between body and heading
doing little independent work. The surviving four-step ramp has real,
unambiguous perceptual jumps: 11 → 13 → 18 → 22.

| Step | Size | Weight | Line-height | Letter-spacing | Used for |
|------|------|--------|-------------|------------------|----------|
| `text-micro` | 11px | 400 | 1.35 | 0 | Meta labels, badges, `.sec-t` uppercase labels, PK/verified pill text, column type annotations, table sub-labels, breadcrumbs |
| `text-base` | **13px** | 400 (regular) / 600 (semibold) | **1.45** | 0 | Default body copy, table rows, inputs, buttons, node titles, list items — the default for nearly all UI. Semibold `text-base` (600) carries any role that previously wanted a distinct in-between size (e.g. emphasized body, section intros) — weight substitutes for size here, see note below |
| `text-heading` | 18px | 600 | 1.3 | -0.006em | Inspector title, card headline, panel titles, section headings |
| `text-display` | 22px | 600 | 1.25 | -0.01em | Page/destination-level titles (introduced for Phase 2's shell, defined here for completeness) |

**Weight/colour substitutes for a fifth size.** Where a role genuinely needs a
distinction between body (13px) and heading (18px) — e.g. the old
"emphasized body, section intros" job that a removed 15px step used to
do — that distinction is expressed with **weight** (`text-base` at 600
instead of 400) or, where an even quieter distinction is needed, a **colour
tier** (`--color-text-secondary`/`--color-text-tertiary` instead of
`--color-text-primary`), never with a new size. This is a deliberate,
permanent substitution — later phases must not reintroduce a fifth size to
solve this class of problem; reach for weight or colour tier first.

### Legacy-size retirement mapping (DS-03 — every scattered value gets an explicit destination)

All six legacy pixel values found scattered across the current app collapse
onto the four surviving tokens below. None are dropped silently — every one
has a stated destination, and where two-plus legacy values land on the same
token, the distinction that mattered (if any) is now carried by weight or
colour tier, not by size:

| Old scattered value | Old usage | New destination | How the original distinction (if any) is preserved |
|---|---|---|---|
| `10.5px` | `.src-chip`, badge/pill text | `text-micro` (11px), regular | Same job, same tier — no distinction was needed against the next row |
| `11.5px` | `.col .name` (column type labels) | `text-micro` (11px), regular, `--color-text-secondary` | Softer emphasis than the 13px body tier is now carried by colour tier, not a smaller size |
| `12.5px` | Breadcrumbs, table sub-text | `text-micro` (11px), regular, `--color-text-tertiary` for the quietest sub-text instances | Same reasoning as above — colour tier carries the "quieter than body" job that a near-duplicate size used to |
| `13px` | `.title`, body copy | `text-base` (13px), regular | Unchanged — already the systematic body size |
| `14px` | Emphasized body, section intros | `text-base` (13px), **semibold (600)** | Weight substitutes for the old size difference — see Weight/colour substitutes above |
| `17px` | `.insp-title h2`, inspector/section headings | `text-heading` (18px), semibold | Rounds up to the nearest surviving step — the 1px difference is imperceptible and heading already carried 600 weight |

**Mono type** (`--font-mono`, Geist Mono Variable): reuses `text-micro` and
`text-base` only — identifiers, GUIDs, column names, and transform
expressions never need a heading-sized mono. Mono letter-spacing is always
`0` (never inherits a heading's negative tracking).

**Weights — exactly two, per the design-contract discipline**: `400` (regular)
and `600` (semibold). The current app's arbitrary `560`/`620` weight values
(tuned to look right specifically in SF Pro, which never actually rendered on
Windows) are retired — `600` reads as visually equivalent semibold in Geist
and is the only "emphasis" weight in the system. The liked segmented-control
active state (`.seg button.on { font-weight: 560 }`) carries forward at `600`
in the new token vocabulary — visually indistinguishable to the eye, now
systematic.

### Font loading strategy (DS-06 — no layout shift, no FOIT)

1. **Install**: `@fontsource-variable/geist` + `@fontsource-variable/geist-mono` (v5.3.0, per STACK.md — pre-subset `latin` woff2, `font-display: swap` already baked into the shipped `@font-face` blocks).
2. **Import once**, in the app's single CSS entry point (not per-component): `@import "@fontsource-variable/geist";` and `@import "@fontsource-variable/geist-mono";`
3. **Preload** the variable-weight file in `index.html`:
   ```html
   <link rel="preload" as="font" type="font/woff2" crossorigin
     href="/node_modules/@fontsource-variable/geist/files/geist-latin-wght-normal.woff2">
   ```
   (confirm the exact path against the installed package's `files/` directory — Fontsource's variable-axis file naming is stable but versioned).
4. **`font-display: swap` + preload together**: preload alone still risks a brief FOIT before the browser has room to swap; `swap` alone still risks a visible fallback-font flash without preload shrinking the window. Both together is the DS-06 fix.
5. **Fallback stack — generic only, never re-tuned**: `--font-sans: "Geist Variable", "Geist", ui-sans-serif, system-ui, sans-serif;`. This is the direct fix for Pitfall 18 — the current `--sans` stack lists `-apple-system, BlinkMacSystemFont, "SF Pro Text", "SF Pro Display"` before any generic fallback, none of which resolve on Windows, and the fallback that silently wins today (`Segoe UI`) was never a deliberate choice. **No weight, letter-spacing, or size value anywhere in this system may be hand-tuned to only look right in the primary font** — that is exactly how the current bug happened and would recur identically for Geist if it silently failed to load.
6. **`font-synthesis: none;`** on `:root` — Geist Variable ships real weights across its whole axis; synthetic bold/italic synthesis is never needed and can produce visible artifacts if a fallback font is substituted.
7. **Verification step (mandatory, not optional)**: check the *computed* `font-family` in Windows 11 devtools (`document.fonts.check('13px "Geist Variable"')` or inspecting `getComputedStyle` on a real text node) as an explicit UAT step for this phase — per Pitfall 18, a silently-failing self-hosted font is the same class of bug as the one this milestone exists to fix, and it is specifically easy to miss by "it looks fine at a glance."
8. **No custom subsetting** beyond Fontsource's default `latin` subset unless a bundle-size audit later shows the font payload (~80–110KB per variable family) is a real problem.

## Spacing Scale (DS-04)

Declared values (multiples of 4, per the locked 8/12/16 rhythm):

| Token | Value | Usage |
|-------|-------|-------|
| `space-1` | 4px | Icon gaps, inline padding, tick-dot margins |
| `space-2` | 8px | Compact element spacing — primary rhythm unit |
| `space-3` | 12px | Default control padding (buttons, chips) — primary rhythm unit |
| `space-4` | 16px | Default section/element spacing — primary rhythm unit |
| `space-6` | 24px | Section padding |
| `space-8` | 32px | Layout gaps |
| `space-12` | 48px | Major section breaks |
| `space-16` | 64px | Page-level spacing (e.g. the lineage view's column-to-column gap) |

**Density primitives** (locked): `--row-height: 28px` (column rows, list items,
search results); base body text at 13px/1.45 sits comfortably inside that row
height with room for vertical centering.

**Exceptions**: icon-only interactive targets (e.g. a bare close/expand icon
button with no text) get a minimum **44×44px** hit target for touch/pointer
accessibility even though the visual glyph stays small and the 28px row
rhythm continues around it — achieved via padding, not by inflating the
row height itself. This is the only sanctioned exception to the 4px-multiple
discipline being violated *visually* — the hit target itself is still a clean
multiple of 4.

## The Locked Per-Canvas Colour Rule (restated as a contract, not a preference)

This is the single most important rule in this document and the direct fix
for THEME-05. **Exactly one hue channel is "primary" per canvas at a time —
never two simultaneously — and state is always cyan + opacity on both:**

| Canvas | Hue carries | Secondary treatment | State |
|--------|------------|----------------------|-------|
| **Lineage DAG** | Edge type (`--color-edge-reads/writes/derives`) | Domain shown as a **thin colour strip** on the table card (`--color-domain-*`), never as the card's fill/background hue | `--color-accent` + opacity: traced = 100% opacity + increased stroke-width, dimmed = ~12% opacity |
| **Knowledge Graph** | Domain (`--color-domain-*`) + a domain-colour legend (GRAPH-06, the one legend the user wants) | Edges render **neutral grey** (`--color-border` or `--color-text-tertiary` weight, no domain/edge-type hue at all) | `--color-accent` + opacity: identical mechanism |

Both canvases still need every domain AND every edge-type token defined —
this rule governs *which channel gets to be the primary visual hue on which
canvas*, not which tokens exist. A DAG card's domain strip and a knowledge-
graph node's fill both read `--color-domain-bronze`, for instance; they just
occupy different visual roles (thin strip vs. full node fill).
